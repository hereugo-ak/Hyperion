# Fix: SearXNG returns 0 results → sub-agents return 0 findings

## Context (root cause, confirmed)
The sub-agents and competitive-intel specialist keep returning "0 findings" /
"Zero competitors found in public sources". Prior fix0.1/fix0.2 commits addressed
SearXNG **startup/readiness/resilience** (`restore SearXNG runtime readiness`,
`restore replica startup`, `recover provider and search failover`) and agent
**orchestration** (structured findings, tier borrowing, retry escalation) — never the
actual cause. The docker logs show the real failure is in the SearXNG retrieval tier:

```
hyperion-searxng-web       searx.engines.brave: Too many request (suspended_time=180)
hyperion-searxng-reference searx.engines.wikipedia: Too many request (suspended_time=180)
```

Two compounding SearXNG config defects cause the corpus to collapse to zero:

1. **`outgoing.request_timeout: 6.0` is shorter than every engine's own `timeout` (8–10s).**
   In all three profiles the HTTP client truncates each upstream request at 6s before
   the engine's 8–10s budget elapses. Under the parallel sub-agent fan-out (6 sub-agents ×
   ~15 queries), upstream latency routinely exceeds 6s, the requests are cut, engines
   report unresponsive, and the discovery corpus returns nothing.
   - web: mojeek 10, mwmbl 10, brave 8, yep 10
   - reference: wikipedia 6, openstreetmap 8, github 8, stackexchange 8, hackernews 6
   - scholar: arxiv 10, crossref 8, openalex 8, semantic_scholar 8, pubmed 8
   ALL are capped at 6s by `outgoing.request_timeout`.

2. **Primary engines are the ones that rate-limit a shared datacenter IP.** The web
   profile's primary is Brave (scraper) and the reference profile's primary is Wikipedia;
   both 429 a datacenter IP (`suspended_time=180`, confirmed in logs). The three replicas
   share ONE public IP (docker-compose.yml comment: "Replicas add capacity and fault
   isolation, not IP-ban evasion"), so there is no IP diversity. The IP-tolerant engines
   (mojeek, mwmbl) and scholarly APIs (crossref, openalex, arxiv, pubmed, semantic_scholar)
   exist but are coupled with the rate-limited scrapers or isolated in the scholar profile
   out of reach for general/competitor queries.

Jina + Google grounding keys are already present (confirmed by user), so the fallback
chain in `SearxNGClient.search` is fine — the problem is the PRIMARY SearXNG tier returns
nothing because of (1) and (2).

## Changes

### 1. Fix the request-timeout misconfiguration (highest impact)
In `searxng_settings.web.yml`, `searxng_settings.reference.yml`, `searxng_settings.scholar.yml`:
- Set `outgoing.request_timeout` to `15.0` (>= max engine timeout + fan-out headroom).
- Set `outgoing.max_request_timeout` to `20.0`.
- Lower each engine's own `timeout` to sit just under `request_timeout` (e.g. 10–12) so a
  single slow engine cannot block a 15s window, but is no longer truncated at 6s.
Same edit applies to the generator `hyperion/infra/searxng_profiles` if these files are
generated (header says "GENERATED by hyperion.infra.searxng_profiles; do not hand edit").

### 2. Rebalance the engine mix to IP-tolerant engines
- web profile: make **mojeek + mwmbl** the reliable primary; demote **brave** (scraper) to
  fallback only (or switch to Brave Search API via `BRAVE_SEARCH_API_KEY` if available);
  drop `yep` (requires `YEP_API_KEY`, currently unset → always fails).
- reference profile: demote **wikipedia** to fallback (definitional only, rate-limits
  datacenter IPs); primary = openstreetmap/github/stackexchange/hackernews.
- Make scholarly/IP-tolerant APIs reachable for general queries: add `crossref` + `openalex`
  to the web profile (or route `general` category to a tolerant set), since crossref/openalex
  tolerate datacenter IPs and answer business/company questions well.

### 3. Loosen the client-side per-engine throttle
`hyperion/tools/searxng.py` `EngineTokenBucket.interval_seconds = 2.0` serializes each
engine to 1 request / 2s process-wide. Under the 6-sub-agent fan-out this starves the
tolerant engines. Lower to ~0.5s for tolerant engines (mojeek/mwmbl/crossref/openalex/…) or
make the interval engine-class aware; keep a stricter interval only for known-fragile
scrapers (brave/wikipedia) if still used.

### 4. Ensure engine-health cooldowns persist and rotate
Confirm `vault/engine_health.json` is written when a `suspended_time=180` ban is recorded
(`engine_health.record_response` → `_save`). A 180s Brave/Wikipedia ban must keep them cooled
so the tolerant engines carry the load instead of re-hitting the banned scraper. If the
state file is empty in a fresh checkout, verify the runtime path is correct and writable.

## Validation
- **Unit/contract test** (add to `tests/`): parse each `searxng_settings.*.yml` and assert
  `outgoing.request_timeout >= max(engine.timeout)` for every profile. Assert the web profile
  does not list `brave`/`wikipedia` as a non-fallback-only engine without a key. This locks in
  the fix and fails CI if regenerated config reintroduces the 6s cap.
- **Live smoke test**: with the stack up, for each profile run one `/search?format=json` query
  and assert `results` is non-empty (e.g. `india automotive market size` on web, a definitional
  query on reference, a paper query on scholar). Then run one short engagement and confirm
  sub-agents return >0 findings (not "research_gap").
- **Regression check**: confirm the prior "0 findings" engagement types (competitive_intel,
  regulatory, risk, ops, consumer, esg) now return structured findings.

## Out of scope
- Provisioning new API keys (Jina/Google already present; Brave API key optional).
- Agent-orchestration code (sub_agent.py / competitive_intel.py) — it is correct; the corpus
  it receives was empty.
- Adding IP-diversity proxies (docker-compose already states replicas share one IP by design).
